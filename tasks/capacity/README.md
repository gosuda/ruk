# Capacity harness (dev-scale scaffold)

Measures the workloads of the Forgejo-realistic profile that are runnable on
this host today, against both system git (baseline) and ruk (subject, same
CLI verbs via `ruk git`, the parity-harness invocation pattern).

Contract sources (read these first; numbers here are their shape, not a copy):

- `local://ruk-reference-production-profile.md` — reference deployment,
  fixture shape, offered load, budgets, acceptance thresholds, run protocol.
- `local://ruk-forgejo-scale-plan.md` — measurement contract, required
  workloads, mandatory structural gates.

## What it measures

`run.sh` runs seven CLI-level workloads, W warm-ups + R measured reps each,
and records offered / completed / rejected plus p50/p95/p99 wall latency:

| workload | command | profile analogue |
|---|---|---|
| `adv-1k` / `adv-10k` | `show-ref` (full) + byte size | ref advertisement at branch steps (dev: 1k/10k) |
| `lookup` | `rev-parse --verify refs/heads/b005000` | exact branch/ref lookup |
| `page1` | `branch --list`, first 20 rows | first branch page |
| `write` | 1-file `add` + `commit` | small write (<=32 paths) |
| `clone` | bare `clone file://` of large-10k | clone stream (stand-in) |
| `fetch` | incremental `fetch` (+1 branch) | fetch stream |

`gen-fixture.sh` builds the fixture deterministically (seed `0x52554b01`,
`--shape mixed` default: even branches share the tip, odd branches get
distinct commits): N small repos + one `large-K` repo per branch-count step.
`check-structure.sh` greps the tree for the mandatory-structural mechanisms
(admission bounds, refusal codes, durability, idempotency, auth) and labels
each STATIC-PRESENT / ABSENT / NEEDS-RUNTIME-PROOF.

`RESULTS.md` is generated by `run.sh` from its own observed output (same
pattern as the parity harness rewriting `GAPS.md`); do not hand-edit it.

## Dev-scale vs profile-scale (honest gap)

This box is NOT the reference deployment (32 cores / 128 GiB / NVMe /
10 GbE, separate load host). Every number here is **dev-scale**:

- Fixture: small repos hold ~20 × ~1 KiB files, not 16 MiB median; the large
  repo has 200 base commits, not 10M commits / 500k paths; branch steps run
  are 1k/10k, not 100k/1M (those need `--full` on a full-profile host).
- Load: isolated CLI ops (3 warm-ups + 10 reps), not 5-min warm-up + 30-min
  steady 1000 ops/s open-loop load with heavy jobs and compaction.
- Path: CLI verbs, not end-to-end Forgejo HTTP/API or Git transport against
  the daemon; there is no admission layer at the CLI, so
  offered=reps/admitted=reps/rejected=0 by construction. Real admission
  accounting (E_LIMIT, queue waits, 429/503) needs the daemon + generator.
- Backend comparison: the ruk side needs a working `ruk` binary. If the
  build is broken (as on the first run — see RESULTS.md), the ruk rows
  record BLOCKED with the reason and the git baseline still runs.

## What remains for a full-profile run

1. `--full` fixture (100k/1M branches, GiB-scale repos) on a 32-core /
   128 GiB reference host with pinned Forgejo + PostgreSQL.
2. Open-loop load generator at 1000 protected ops/s + heavy jobs
   (8 clone/fetch, 4 blame, 4 merge, compaction) with offered/admitted/
   completed/rejected/timeout/cancelled split and queue-time accounting.
3. Burst (3x, 10 min), recovery (60 s), hot-repository, 6-hour soak, and
   crash-around-publication scenarios.
4. HTTP 429/503 mapping checks and per-request 1 GiB / 30 s advertisement
   budget proof at 1M branches.
5. `ruk forgejo serve` daemon tasks (admission classes, bulk workers) are
   product work outside `tasks/capacity/`; gaps found here are reported,
   not implemented.

## Usage

```sh
bash tasks/capacity/gen-fixture.sh --out /tmp/cap-fix --small 4 --branches "1000 10000"
bash tasks/capacity/run.sh --fixture /tmp/cap-fix --reps 10 --warmup 3
bash tasks/capacity/run.sh --fixture /tmp/cap-fix --hyperfine   # needs hyperfine(1)
bash tasks/capacity/check-structure.sh
```

On shell rules: scripts use the strict preamble, quoted expansions, guarded
`rm -rf -- "${var:?}"`, and `printf`. `shellcheck`/`shfmt`/`bats` are not
installed on this host, so gating on them is deferred to CI.
